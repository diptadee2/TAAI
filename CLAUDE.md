# TAAI website — project context

GATE DA 2027 exam-prep marketing site for TAAI (live at taai.live; LMS is a separate app at learn.taai.live, not in this repo).

## Tech stack

- Plain HTML + inline `<style>` + JSX, no bundler. Each of the 6 main pages is fully self-contained: nav, footer, and all components are copy-pasted JSX inside that page's own `<script type="text/babel">` block.
- `build.mjs` precompiles the JSX (via `@babel/core` + `@babel/preset-react`) into plain JS and writes the result to `dist/`, which is what Netlify deploys (`netlify.toml`: `publish = "dist"`).
- Local dev serves the **source root directly**, not `dist/` — source pages still have Babel Standalone (`<script type="text/babel">`) and load React/ReactDOM from a CDN, so they transpile live in-browser. This means editing a page and refreshing works with no build step, but it also means anything that only exists in `dist/` (generated output) is invisible to the dev server unless it's also written into source.

## Commands

- `npm run build` — compiles pages + regenerates the blog + sitemap into source, then copies everything to `dist/`.
- `npm run watch` — same, plus rebuilds a page's compiled output when its source file changes.
- Local preview: a static server pointed at the **project root** (not `dist/`), typically on port 8080.

## Pages

`index.html`, `gate-da-courses.html`, `gate-da-test-series.html`, `gate-da-toppers.html`, `contact.html`, `gate-da-free-notes.html`, `gate-da-progress-tracker.html` — each listed in `PAGES` in `build.mjs`. Clean URLs (`/gate-da-courses`, etc.) are handled by redirects in `netlify.toml`, with 301s from the old short names (`/courses`, `/test-series`, `/testimonials`, `/resources`) and from `.html` extensions so old links don't break — `gate-da-progress-tracker.html` is the exception: it was renamed from `progress.html`/`/progress` on 2026-07-25 with no redirect from the old slug at all, by request. `gate-da-free-notes.html` fetches notes/lecture metadata at runtime from published Google Sheet CSVs (`sheets/` holds local snapshot templates, gitignored). `gate-da-progress-tracker.html`'s main content (not its nav, which matches the other pages) is the one exception to the "JSX per page" rule below — see the Progress tracker section.

## Blog (added 2026-06-27)

Static, no backend/database. Source of truth is `content/blog/*.md` (frontmatter + Markdown).

- `build.mjs`'s `generateBlog()` reads those files and writes plain static HTML (no JSX/Babel involved) into the **source** `blogs/` folder: `blogs/index.html` (listing) and `blogs/<slug>/index.html` (each post) — written to source rather than `dist/` specifically so the source-serving dev server can preview it like every other page. The generic asset-copy step in `build()` then carries `blogs/` into `dist/` for the real deploy.
- These generated files (`blogs/index.html`, `blogs/*/`) and the root `sitemap.xml` are gitignored — they're build artifacts regenerated from `content/blog/`, same logic as `dist/` itself not being committed.
- Visual design is shared via `blogs/blog.css` (extracted design tokens/nav/footer from the main pages, plus blog-specific styles matching the site's offer-card visual language — gradient hero blobs, gradient `<em>` emphasis, top-strip+icon-badge cards) and `blogs/blog.js` (vanilla JS: mobile hamburger menu, scroll progress, back-to-top, fade-in reveal — a deliberately simplified stand-in for the React pages' nav, since duplicating the full stateful Nav component's hover-pill/signin-cycle animations wasn't worth it for content pages).
- `sitemap.xml` is generated dynamically (was a hand-maintained static file before) and includes every post automatically.
- `/admin` is Decap CMS (`admin/index.html` + `admin/config.yml`), backend `git-gateway` — a non-technical writer logs in (Netlify Identity, optionally via Google as an external provider) and publishing commits a Markdown file straight to `content/blog/`, which triggers a normal Netlify rebuild.
- **"Blocks" — a fill-in-the-blanks system so a non-technical writer can build a data-rich post (charts, tables, FAQ, diagrams) without touching HTML/CSS** (added 2026-09-04, after an initial hand-coded version of `gate-da-syllabus-2027` — its own custom fonts/colors/SVG charts, all raw HTML in the Body field — made clear that level of design isn't something the plain Markdown editor can produce, nor something to expect from a non-technical writer). **`gate-da-syllabus-2027` itself was then rebuilt on Blocks once the system existed** (same day) — explicitly, since keeping the one showcase post as a hand-coded exception would defeat the point; it now uses the standard site design (`--purple`/`--pink`/etc.) like every other Blocks post, not its original bespoke look, and is safe to open and edit through `/admin` normally, unlike a raw-HTML post would be. In `/admin`, a post's optional **Blocks** field (`admin/config.yml`, a Decap "variable types" list) lets the writer add, in any order, any number of: Section heading, Paragraph text, Bar chart, Grouped bar chart, Line chart, Data table, Step diagram (things accumulating over steps), Two-path diagram (one thing splits into two outcomes), Comparison rows, Two-column comparison, Syllabus/topic grid, FAQ, or Resource links — each just plain labels/numbers/text fields, rendered into the actual chart/table/diagram by `renderBlocks()`/`BLOCK_RENDERERS` in `build.mjs`, styled by the `.block-*` rules appended to `blogs/blog.css` (using the site's own existing `--purple`/`--pink`/`--blue`/etc. tokens, plus two new ones — `--rise`/`--fall` — added specifically for chart trend coloring). Rendered after the regular Body field, in the order the writer added them. Bar/line/grouped-bar charts size themselves as a % of the block's own data (its min/max), not fixed pixel coordinates — required since block data is arbitrary and unknown ahead of time, unlike a hand-tuned one-off chart. **Scope was a deliberate, explicit call**: templatize everything from the source article, including the illustrative diagrams (step/two-path/comparison), not just the obviously-reusable data charts — the "Two-column comparison" block is a knowingly simplified stand-in for the one figure that didn't reduce to structured data at all (a hand-drawn "scattered dots vs. one connected line" illustration) — that one visual metaphor specifically isn't reproduced, everything else is.
  - **`blocks_json` — a paste-from-LLM path added 2026-09-04, once it was clear the manual Blocks list itself (click "Add" per block, then hand-type into every field) was still too much friction for a non-technical writer, who realistically drafts with an LLM anyway.** A second, optional frontmatter field (`admin/config.yml`, a Decap `code` widget with `output_code_only: true` so it stores as a plain string) holds one pasted JSON array describing all of a post's blocks in one shot; `loadPosts()` in `build.mjs` uses it in place of the manual `blocks` list whenever it's non-empty (checked first, falls back to `blocks` only if empty) — same field names/shapes as the manual list, just JSON instead of clicking through the UI. Malformed JSON here throws and fails the whole build, naming the offending post file — deliberate, since this runs at build time (not in front of a live user), so failing loudly here beats silently shipping a post with blocks missing. `admin/index.html`'s `LLM_PROMPT_TEXT` is the actual prompt a writer copies into ChatGPT/Claude alongside their source article — transcribed by hand from the same 13 renderer functions' field contracts, shown in a copy-ready textarea above the existing Blocks reference cards in the preview pane. Verified end-to-end with a throwaway test post (`blocks_json` covering 5 block types, screenshotted rendering correctly, then a deliberately-broken JSON string confirmed the build fails with a clear file-named error) before being deleted, never committed. **Keep `LLM_PROMPT_TEXT` in sync by hand** whenever a block type's fields change in `build.mjs`/`admin/config.yml` — same maintenance burden `BLOCKS_REFERENCE_HTML` already has, now doubled.
  - **Nested Blocks data forced a real YAML parser** — `parseFrontmatter()` used to be a hand-rolled regex parser that only understood a flat list of scalar strings under one key (fine for the original `tags` field); it would have silently mis-parsed or dropped Blocks' nested lists-of-objects-containing-their-own-nested-lists. Replaced with `js-yaml` (pinned to **`4.x`**, not the newer `5.x` — that major version's API is a ground-up rewrite with no default export and a very different, lower-level surface not needed here; confirmed by hitting `SyntaxError: ... does not provide an export named 'default'` on first install). A field from a Decap list using a single `field:` (not `fields:`) serializes as a plain array of values — e.g. `series`, `x_labels`, `columns`, any `values` list; mixing this up with an object-array field (`fields:`, plural — e.g. `bars`, `steps[].items`) silently reads `undefined` off a plain string, so `build.mjs`'s block renderers deliberately handle the two differently per field, not uniformly.
- **`/gate-da-subjects.js` (project root) is the single source of truth for the GATE DA subject list/order** (added 2026-09-04, after 3 separate hand-maintained copies — the tracker, `/team`, and the blog's tags — had already drifted out of sync once) — defines `window.GATE_DA_SUBJECTS`, a plain array of 10 names with no emoji/styling (must match `schedule_tasks.subject` exactly, since `progress.js` matches real schedule data by this string). If the subject list ever changes, update `/gate-da-subjects.js` first, then `admin/config.yml`'s tags by hand to match.
- **Blog tag list matches the tracker's subject list exactly** — `admin/config.yml`'s `tags` options used to have one combined "Python & DSA" tag; split 2026-09-04 into separate Python/Data Structures/Algorithms tags specifically to match the centralized subject list above, rather than three different subject breakdowns existing across the site. No existing posts referenced the old `python-dsa` tag at the time (checked `content/blog/` directly), so this was a clean rename, not a migration.
- **`gate-da-syllabus-2027` gets a deliberate internal link from `index.html`'s and `gate-da-courses.html`'s hero sections** (`.hero-guide-link`, added 2026-09-06) — a small "📘 New: Free GATE DA Syllabus 2027 guide" line under each page's primary CTA buttons, added specifically for SEO: before this, the post was only reachable via `/blogs`, meaning zero internal link equity flowed to it from the site's two highest-authority pages. Deliberately unobtrusive (small text link, not styled as a competing CTA) and placed after the real conversion buttons, not before. Don't remove this without adding an equivalent link elsewhere — the point is to keep at least one high-authority internal link pointing at this post. `lastmod` in the generated sitemap is intentionally NOT bumped just because of this — it should only change when the post's own content changes, not when other pages link to it.
- **Known gotcha**: Decap CMS resolves `config.yml` as a relative URL. Visiting `/admin` without a trailing slash makes the browser resolve it against `/` instead of `/admin/`, 404ing regardless of browser — fixed via `<base href="/admin/">` in `admin/index.html`. Don't remove that tag.
- Netlify Identity + Git Gateway + the Google login provider are dashboard-only settings, not something committable — and Identity login only works on a real deployed domain, never on `localhost`.

## Progress tracker (`/gate-da-progress-tracker`, added 2026-07-21; slug renamed from `/progress` 2026-07-25 with no redirect from the old path)

A day-by-day study schedule tracker at `taai.live/gate-da-progress-tracker`, open to any student (no LMS/enrollment check — this is intentionally separate from `learn.taai.live`). First real backend/database this repo has ever had; everything else in this site is static.

- **Frontend**: `gate-da-progress-tracker.html` + `progress.js`. The nav is React/JSX ported verbatim from the other pages (added 2026-07-24, scoped light-theme CSS vars on `#nav-root` so it doesn't leak into this page's dark theme) — but the tracker itself (calendar, streak, pomodoro, etc.) is vanilla JS, no React/Babel. `progress.js` renders that part by building HTML strings and setting `innerHTML`, not a framework.
- **Backend**: Supabase (Postgres) accessed only through Netlify Functions in `netlify/functions/` — the frontend never talks to Supabase directly. `lib/supabase.js` and `lib/csv.js` hold shared helpers. Functions: `register`, `complete-task`, `streak`, `subject-progress`, `pomo-settings`, `pomodoro-complete`, `pomodoro-leaderboard`, `rename`, and `tracker-data` (a single consolidated endpoint for the page-load batch — see the gotcha below; it replaced 4 separate one-off functions that used to exist here: `schedule`, `progress`, `last-week-focus-leaders`, `pomo-sessions`).
- **Student identity**: cookie only (`taai_user`, base64-encoded JSON, 365-day expiry), no passwords/auth. `register.js` looks up-or-creates by email.
- **Schedule data flow — deliberately manual, no automatic external sync of any kind.** The user hands over each month's schedule directly (as a PDF or similar); convert it to `sheets/schedule.csv` (`Date | <Subject columns...>`, dates as `DD/MM/YYYY`, one cell = one task) and run `npm run load-schedule` (`scripts/load-schedule.mjs`) to load it into Supabase — validate through the real `parseCsv`/`toIsoDate` in `netlify/functions/lib/csv.js` first, don't hand-write SQL. There used to be a `sync-schedule.js` cron function pulling from a published Google Sheet; removed at the user's explicit request ("I will provide you the schedules, don't read from anywhere else") — don't reintroduce an automatic fetch from Sheets or any other external source without being asked.
- **Streak** (`streak.js`) and **subject-progress** (`subject-progress.js`) are both computed from the *entire* schedule history server-side, not from whatever month the client currently has loaded — a month-scoped version would make progress look like it resets every time the student navigates months, since e.g. a subject can span many months and a streak must span backward past the currently-viewed month.
- **"Progress by subject" always shows the full GATE DA syllabus**, not just subjects that happen to be scheduled yet — `CANONICAL_SUBJECTS` in `progress.js` is a hardcoded display-name list merged with whatever `subject-progress.js` actually returns; unscheduled ones show at 0%. Names are matched by exact string, so if a future month's sheet spells a subject differently than `CANONICAL_SUBJECTS` (or differently than an already-synced month did), it'll show up as an extra row instead of merging — keep this list's spelling in sync with whatever's actually typed into schedule PDFs/CSVs.

## Discord bot + /team console (added 2026-08-29 through 2026-09-02)

Posts to Discord automatically, reusing the progress tracker's existing leaderboard data. **Rearchitected 2026-09-02** from 3 hardcoded, fixed-cron functions into a general scheduler (`scheduled_posts` table + `discord-dispatch.js`), managed from a new authenticated page (`/team`) — driven by the ask to control "any post in any channel... text, tagging, date, time, frequency, repeatability," not just the original 3.

- **Why a dispatcher, not one cron per post**: Netlify Scheduled Functions run on a cron baked into `netlify.toml` at *deploy* time — a page can't change when a function fires, only what it does when it fires. So a user-editable schedule can't map to "one cron per post." Instead, `netlify/functions/discord-dispatch.js` runs on one fixed, frequent cron (`*/15 * * * *`, every 15 minutes — see `netlify.toml`) and queries `scheduled_posts` for anything due (`enabled AND next_fire_at <= now()`), firing each row independently (one row's failure doesn't block the others) and recomputing `next_fire_at` for recurring types via `computeNextFireAt()` in `lib/supabase.js` (`'once'` posts just get `enabled = false` instead).
- **`scheduled_posts`** (`supabase/schema.sql`): one row per post. `source` is either `'custom'` (literal `title`/`body` text) or one of 4 built-in dynamic sources — `'daily_leader'` (yesterday's single top student), `'daily_leaderboard'` (yesterday's top 3, added 2026-09-02 once a single winner wasn't enough), `'weekly_leaderboard'` (last week's top 5), `'monthly_consistency'` — which pull live data via the same `fetchTodayLeaders`/`fetchLastWeekLeaders`/`computeMonthlyConsistency` helpers the tracker page itself uses. `title`/`body` are always an optional override template (via `renderTemplate()`) that falls back to the original hardcoded wording when blank. Placeholders: the single-entity sources (`daily_leader`, `monthly_consistency`) get `{{name}}`/`{{hours}}` for the one student, and `body` there fully replaces the default sentence when set. The ranked-list sources (`daily_leaderboard`, `weekly_leaderboard`) get per-position placeholders instead — `{{name}}`/`{{hours}}` for 1st, `{{name2}}`/`{{hours2}}` for 2nd, up through `{{name5}}`/`{{hours5}}` for the weekly top 5 (see `rankedVars()` in `discord-dispatch.js`), an unmatched placeholder (e.g. `{{name4}}` on a top-3 post) just rendering blank rather than erroring — but there, `body` is only an **intro line shown above** the medal list, never a replacement for it (the list itself always renders, by request, matching how `monthly_consistency`'s intro + runner-up list already worked). Each row carries its **own** `webhook_url` — not the shared `DISCORD_WEBHOOK_URL` env var — so different posts can genuinely target different channels; the env var is only `postToDiscordWebhook()`'s fallback default for any caller that doesn't pass one explicitly.
- **Monthly "most consistent student"** (the `'monthly_consistency'` source, reports on the month that just closed — an Oct 1 firing reports September): ranks by **median** daily focus minutes, zero-filled across every calendar day of the month (every day counts as a real work day here, no rest-day concept exists in this schedule), not a raw average, so one huge binge day can't outrank someone who studied moderately but genuinely every day. Only students registered by the **7th** of that month are eligible. Ties broken by total minutes. **August 2026 was deliberately never computed** — `pomo_daily_sessions.total_minutes` only started actually populating on Aug 28 (see the known-gotcha below), so a full-August calculation would zero-fill 27 of 31 days for nearly every student regardless of real activity.
- Built-in sources link back to `https://taai.live/gate-da-progress-tracker` two ways: the embed title itself (Discord makes a titled embed's `url` clickable) and an explicit `[📊 View the progress tracker](...)` markdown link line in the body.
- **`/team`** (`team/index.html` + `team/team.js`) — the only place `scheduled_posts` rows are ever created/edited/deleted (`netlify/functions/team-posts.js`, a role-gated REST-style CRUD function: GET/POST/PUT/DELETE). Gated by **Netlify Identity**, the same login already powering the blog CMS at `/admin` — but requiring the **`admin` role specifically** (`requireAdmin()` in `lib/supabase.js`, checking `context.clientContext.user.app_metadata.roles`), not just "any logged-in Identity user", since a blog writer sharing that same login has no reason to reach student data or webhook controls. ## Known gotchas worth not re-discovering

- **A blog post's Markdown body can embed raw HTML (`marked` passes it through), but every line must start at or near column 0** — CommonMark treats a line indented 4+ spaces, once it starts a new block (e.g. right after a blank line), as an *indented code block*, not raw HTML, even mid-way through an otherwise-fine HTML section. Hit this directly writing a heavily-nested custom-design post (the original hand-coded version of `gate-da-syllabus-2027.md`, before it was rebuilt on Blocks): several `<div>` blocks silently turned into escaped `<pre><code>` text instead of rendering, purely because they carried the source article's original 4-8 space indentation. Fix: strip all leading whitespace from HTML content going into a post's Markdown body — indentation is a purely cosmetic authoring habit here, not something the renderer tolerates the way a browser parsing plain HTML would. Still worth knowing if a post's Body field (not Blocks) ever needs real embedded HTML again.
- **A post can carry its own bespoke design (fonts, colors, custom `<style>`) safely by scoping every custom property and selector to a wrapper class** (e.g. `.gda-article`) **instead of `:root`/bare `body`** — blog.css already defines `--ink`/`--line`/etc. globally for the shared nav/footer chrome; a post's own `:root{--ink:...}` would silently override those site-wide, breaking the nav/footer's colors, not just the post's own content. Verified this doesn't leak by checking the real computed color of a nav element after loading such a post.
- **Chromium DOM-node leak**: animating `transform` or `box-shadow` directly on an element that *also* has both `box-shadow` and `border-radius` causes an unbounded detached-node leak (confirmed via CDP `Performance.getMetrics`). Animate a wrapper or pseudo-element instead, leave the shadow+radius element itself unanimated.
- **WebGL/Canvas effects are expensive per-tab** (measured via renderer+GPU process RSS, not JS heap — heap snapshots show nothing here): a `gsap`-driven Canvas2D effect cost ~150-200MB/tab from its continuous ticker; an `ogl`-based WebGL shader background cost ~300MB from context creation itself, independent of resolution. A zero-dependency Canvas2D effect with no continuous external library ticker (`DotField` in `courses.html`) showed no measurable cost. Prefer that pattern if a future visual effect request comes in.
- **Dev-server-only memory growth** from repeated live Babel recompilation during active navigation testing is expected and not a leak (confirmed via heap-snapshot diffing) — it does not affect production, since Netlify serves precompiled `dist/`.
- **Favicon**: the 16×16 frame inside any `.ico` built via ImageMagick gets forced to 1-bit alpha regardless of source quality — that's why standalone `favicon-16.png`/`favicon-32.png` exist as preferred `<link rel="icon" type="image/png">` tags ahead of the `.ico` fallback.
- **Server-side "today" must be computed in IST, never naive `new Date()`**: Netlify Functions run on infrastructure with no guaranteed local timezone (effectively UTC). For roughly the first 5.5 hours of every IST calendar day, a naive `new Date().toISOString().slice(0,10)` silently returns *yesterday's* date by IST reckoning — bit us exactly this way in `streak.js` (a same-day tick wasn't counted). Use `todayIST()` in `netlify/functions/lib/supabase.js` (`Intl.DateTimeFormat` pinned to `Asia/Kolkata`) for any server-side calendar-date logic.
- **`@supabase/supabase-js` needs an explicit WebSocket transport**: `createClient()` eagerly constructs a Realtime client requiring a `WebSocket` constructor that isn't guaranteed across every Node/Lambda runtime a function might execute on — without it, every single request crashes. `lib/supabase.js` passes `realtime: { transport: ws }` (the `ws` npm package) to work around this; don't remove it even though nothing here actually uses realtime subscriptions.
- **`tracker-data.js` is deliberately one large function instead of several small ones** — it used to be 7 separate Netlify Functions (`schedule`, `last-week-focus-leaders`, `progress`, `streak`, `subject-progress`, `pomo-settings` GET, `pomo-sessions`), all only ever called together as one batch from `loadMonth()`. Each Netlify Function is an independent Lambda with its own cold-start lifecycle, so a page load after any idle gap paid up to 7 separate container-boot + Supabase-client-construction costs in parallel — confirmed via the Netlify Functions dashboard as the cause of a uniform 1.2-1.8s p50 latency on otherwise-simple single-table queries, plus inflated Web-requests credit usage. Don't re-split this back into one-function-per-query without re-checking whether that dashboard number regresses — `streak.js`, `subject-progress.js`, and `pomo-settings.js` are correctly still separate, since those are also called independently outside the page-load batch (after a task toggle, or a settings save).
- **Local Supabase (`supabase start`) doesn't auto-grant table privileges** the way a hosted project does — a table created via migration has no `service_role` GRANTs by default on the local CLI's Postgres image, so every query fails with "permission denied" even with correct credentials. `supabase/schema.sql` ends with explicit `GRANT SELECT, INSERT, UPDATE, DELETE ... TO service_role` — required for local dev to work at all, keep it even though hosted Supabase might not strictly need it.
- **Any script run with `.env` loaded hits the real production Supabase project, not a sandbox** — there's no separate local/staging database (see "Local dev needs `netlify dev`, not Docker" above). Seeding synthetic test rows directly via `getSupabase()` (rather than through `netlify dev`'s served app) is easy to reach for when testing backend logic in isolation, but it's real, live data the instant it's written — confirmed the hard way: seeding 20 fake high-minute `pomodoro_stats` rows to test the leaderboard's below-top-20 behavior briefly *displaced actual students* from the real top-20 leaderboard until cleaned up. Prefer mocking the HTTP response (e.g. Playwright route interception) over seeding real rows whenever the goal is testing frontend rendering; if a backend query genuinely needs live-data verification, clean up every row written immediately after and verify the real leaderboard/data is back to its prior state, not just that the delete call returned success.
- **`.fade-in` elements + a `fullPage` Playwright screenshot taken without scrolling can look like missing content** when they're actually present and correct — the IntersectionObserver-driven reveal hasn't fired yet for anything below the fold at capture time. Before treating a screenshot gap as a real bug, either scroll through first or run `document.querySelectorAll('.fade-in').forEach(el => el.classList.add('visible'))` to force-reveal everything, then re-screenshot.
- **Regenerating a `.fade-in` element's `innerHTML` replays its entrance animation from scratch**, even if the only actual change was a number. Hit this repeatedly in `progress.js` (streak card, subject-breakdown, heatmap all did this on every task toggle). Fix pattern used throughout: patch the specific value in place (`el.textContent = ...`, `el.style.width = ...`, `el.setAttribute('data-level', ...)`) instead of regenerating and reassigning a `.fade-in` ancestor's `innerHTML`.
- **Don't try to recolor native `<input type="number">` spin buttons for a dark theme** — tried `color-scheme: dark`, then an explicit `::-webkit-inner-spin-button { filter: invert(1) }`, and the arrows were still low-contrast/black in the user's actual browser both times (couldn't even verify visually in headless Chromium, which renders/suppresses them differently than a real browser). WebKit/Firefox/Safari each handle these hooks inconsistently. Just remove them (`-webkit-appearance: none` on the spin-button pseudo-elements, `appearance`/`-moz-appearance: textfield` on the input) — typing a number directly or the keyboard up/down arrow keys still work with the visual spinner hidden.
- **`CLIENT_VERSION` (the matching constant in `progress.js` and `netlify/functions/lib/supabase.js`) needs bumping on every real client-behavior change to `progress.js`, not only when a request/response payload shape changes.** It drives `checkClientVersion()` in `progress.js`, which polls `/api/version` every 2 minutes and force-`location.reload()`s a tab on a mismatch — the whole point being that an already-open tab picks up a fix automatically instead of running stale JS indefinitely. It went unbumped for 33 days across several real behavior-changing commits (including a genuine race-condition fix to the Pomodoro timer), which silently disabled that safety net for the entire window: `/api/version` kept returning the same string, so the check never tripped, even though the code underneath had materially changed. Any tab left open during that gap never got reloaded onto the fixes. Bump both copies together whenever `progress.js`'s runtime logic changes in any way a student could notice, not just on contract changes.
- **No `[[headers]]` block existed in `netlify.toml` until 2026-08**, so every static asset (images, favicons, the vendor React bundle) inherited Netlify's default `Cache-Control: public, max-age=0, must-revalidate` — the same "always revalidate, never cache" policy meant for HTML — forcing every repeat visit to re-download them in full. This was the single largest driver of Web bandwidth credits (checked via the account's Usage panel, not a guess). Fixed with a 7-day cache for `*.webp`/`*.png`/`favicon.ico`/`vendor/*` only — deliberately excludes HTML and actively-edited JS/CSS (`progress.js`, `blogs/blog.css`/`blog.js`) so shipped fixes keep showing up immediately instead of being stuck behind a stale cache. **`netlify dev`'s local "simple static server" fallback doesn't apply custom `[[headers]]`** even after a restart (confirmed: `curl -I` against localhost:8080 kept showing `max-age=0` post-restart) — this isn't a sign the config is broken, it's a known local-dev-only limitation; the production CDN does honor it. Don't waste time trying to verify cache headers via localhost.

## Future considerations (not started, no code exists for this yet)

**Cost/usage analysis, 2026-09-06** — triggered by a Netlify usage screenshot (Functions compute the dominant line item) and a Supabase usage screenshot (Egress the dominant line item there, 1.442/5GB = 29%, everything else near 0% since this project doesn't use Supabase Auth/Storage/Realtime/Edge Functions at all today). Led to modeling what happens at a hypothetical 300 active students (up from the real ~52 active / 302 total at the time), which reversed the initial instinct on what to fix:

- **Splitting some Netlify Functions to Supabase Edge Functions was floated first, then rejected as the wrong fix.** The mechanism would have worked (a Netlify `[[redirects]]` rule can proxy a path straight to an external URL with zero frontend changes), and `pomodoro-leaderboard.js` (polled every 30s during Focus Mode, no admin auth, the single highest-frequency call in the app) was the identified candidate. **But it doesn't reduce Supabase Egress — likely the opposite.** Today, a request flows browser → Netlify Function → Supabase (query) → Netlify Function → browser; Supabase's Egress meter only counts the middle leg. Moving the function onto Supabase's own Edge Functions means the *entire* response, including the final leg back to the browser, now leaves Supabase's network directly — adding a new chunk of traffic to the meter that's already the real constraint. **Verdict: don't do this.** It solves a problem (Netlify Functions compute) that degrades gracefully at scale, while leaving untouched, or worsening, the one that doesn't (Egress).
- **The real finding: at 300 active students, Egress — not Netlify compute — exhausts the entire monthly free-tier allowance in 1-3 days, not the month.** Modeled by measuring real per-call byte sizes for `pomodoro-leaderboard.js` against live production data (~43.5 KB/call today) and scaling by session-length assumptions; the model's 1-hour/day prediction at the real current 52-active-student count landed within a few days of the real observed 1.442 GB Egress figure, which is a solid confidence check on the methodology.
- **Measured (not guessed) breakdown of that 43.5 KB**: streak-related queries (`scheduledForStreak` + `completedForStreak`) are 33,081 bytes, last-week-rank data (`lastWeekStats`, unbounded — fetches *every* active student's prior week, no `LIMIT`) is 3,568 bytes. Together, **84.2% of every single leaderboard poll's payload** is spent on these two pieces; the genuinely-must-stay-live parts (this week's/today's stats, live status, display names) are only 15.8%, and are already bounded by `LIMIT 10`/`LIMIT 20` clauses so they don't scale with total student count anyway.
- **Database Size is NOT a real concern, structurally, not just because the numbers are currently small.** `pomo_daily_sessions` grows by at most one row per active student per day (an upsert, not a per-completion insert), so it scales with (active students × elapsed days), not with poll frequency or session length the way Egress does. Even at 300 active students for a full year, that's ~18 MB against the 500 MB free-tier cap. Every other table grows even slower (bounded by course content, or weekly instead of daily). Don't re-litigate this one without new information — the growth curve is fundamentally different from Egress's.
- **A "batch-credit everyone every 25 minutes instead of writing on each completion" idea was floated for the write side and rejected** — it targets the wrong path entirely (writes were never the bottleneck; reads via the leaderboard poll are), and is structurally broken regardless: students' Pomodoro sessions aren't synchronized to any shared clock (work-phase duration is customizable per student, 1-180 min), so a fixed global poll would either credit sessions late by up to the poll interval (breaking the immediate-feedback timer/chime) or need to run so often it wouldn't save anything. The current event-driven, write-on-actual-completion model is already correct and cheap; don't revisit this direction.
