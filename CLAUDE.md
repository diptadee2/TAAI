# TAAI website — project context

GATE DA 2027 exam-prep marketing site for TAAI (live at taai.live; LMS is a separate app at learn.taai.live, not in this repo).

## Tech stack

- Plain HTML + inline `<style>` + JSX, no bundler. Each of the 6 main pages is fully self-contained: nav, footer, and all components are copy-pasted JSX inside that page's own `<script type="text/babel">` block.
- `build.mjs` precompiles the JSX (via `@babel/core` + `@babel/preset-react`) into plain JS and writes the result to `dist/`, which is what Netlify deploys (`netlify.toml`: `publish = "dist"`).
- Local dev serves the **source root directly**, not `dist/` — source pages still have Babel Standalone (`<script type="text/babel">`) and load React/ReactDOM from a CDN, so they transpile live in-browser. This means editing a page and refreshing works with no build step, but it also means anything that only exists in `dist/` (generated output) is invisible to the dev server unless it's also written into source.

## Commands

- `npm run build` — compiles pages + regenerates the blog + sitemap into source, then copies everything to `dist/`.
- `npm run watch` — same, plus rebuilds a page's compiled output when its source file changes.
- Local preview: a static server pointed at the **project root** (not `dist/`), typically on port 8080.

## Pages

`index.html`, `gate-da-courses.html`, `gate-da-test-series.html`, `gate-da-toppers.html`, `contact.html`, `gate-da-free-notes.html`, `gate-da-progress-tracker.html` — each listed in `PAGES` in `build.mjs`. Clean URLs (`/gate-da-courses`, etc.) are handled by redirects in `netlify.toml`, with 301s from the old short names (`/courses`, `/test-series`, `/testimonials`, `/resources`) and from `.html` extensions so old links don't break — `gate-da-progress-tracker.html` is the exception: it was renamed from `progress.html`/`/progress` on 2026-07-25 with no redirect from the old slug at all, by request. `gate-da-free-notes.html` fetches notes/lecture metadata at runtime from published Google Sheet CSVs (`sheets/` holds local snapshot templates, gitignored). `gate-da-progress-tracker.html`'s main content (not its nav, which matches the other pages) is the one exception to the "JSX per page" rule below — see the Progress tracker section.

## Blog (added 2026-06-27)

Static, no backend/database. Source of truth is `content/blog/*.md` (frontmatter + Markdown).

- `build.mjs`'s `generateBlog()` reads those files and writes plain static HTML (no JSX/Babel involved) into the **source** `blogs/` folder: `blogs/index.html` (listing) and `blogs/<slug>/index.html` (each post) — written to source rather than `dist/` specifically so the source-serving dev server can preview it like every other page. The generic asset-copy step in `build()` then carries `blogs/` into `dist/` for the real deploy.
- These generated files (`blogs/index.html`, `blogs/*/`) and the root `sitemap.xml` are gitignored — they're build artifacts regenerated from `content/blog/`, same logic as `dist/` itself not being committed.
- Visual design is shared via `blogs/blog.css` (extracted design tokens/nav/footer from the main pages, plus blog-specific styles matching the site's offer-card visual language — gradient hero blobs, gradient `<em>` emphasis, top-strip+icon-badge cards) and `blogs/blog.js` (vanilla JS: mobile hamburger menu, scroll progress, back-to-top, fade-in reveal — a deliberately simplified stand-in for the React pages' nav, since duplicating the full stateful Nav component's hover-pill/signin-cycle animations wasn't worth it for content pages).
- `sitemap.xml` is generated dynamically (was a hand-maintained static file before) and includes every post automatically.
- `/admin` is Decap CMS (`admin/index.html` + `admin/config.yml`), backend `git-gateway` — a non-technical writer logs in (Netlify Identity, optionally via Google as an external provider) and publishing commits a Markdown file straight to `content/blog/`, which triggers a normal Netlify rebuild.
- **`/gate-da-subjects.js` (project root) is the single source of truth for the GATE DA subject list/order** (added 2026-09-04, after 3 separate hand-maintained copies — the tracker, `/team`, and the blog's tags — had already drifted out of sync once) — defines `window.GATE_DA_SUBJECTS`, a plain array of 10 names with no emoji/styling (must match `schedule_tasks.subject` exactly, since `progress.js` matches real schedule data by this string). Loaded via a plain `<script src="/gate-da-subjects.js">` tag placed *before* the consuming page's own script (see `gate-da-progress-tracker.html` and `team/index.html`) — this fits the site's existing no-bundler, plain-`<script>`-tag architecture, and the generic asset-copy step in `build.mjs` already carries any new root-level file into `dist/` with no build-script changes needed. `progress.js`'s `CANONICAL_SUBJECTS` and `team/team.js`'s `SUBJECT_OPTIONS` both read from `window.GATE_DA_SUBJECTS` now (each still falls back to its own hardcoded copy of the same list if that global is somehow missing, purely as a defensive backstop, not a second source of truth to maintain) — `team.js` additionally pairs each name with its own emoji (`SUBJECT_EMOJI`, matched by array position), since that's presentation specific to the Discord post, not part of a subject's canonical identity. **The one place this can't reach**: `admin/config.yml` is YAML consumed by Decap CMS, not JS — it can't load this file directly, so its blog tag list (see below) stays a manually-synced copy with a comment pointing back here. If the subject list ever changes, update `/gate-da-subjects.js` first, then `admin/config.yml`'s tags by hand to match.
- **Blog tag list matches the tracker's subject list exactly** — `admin/config.yml`'s `tags` options used to have one combined "Python & DSA" tag; split 2026-09-04 into separate Python/Data Structures/Algorithms tags specifically to match the centralized subject list above, rather than three different subject breakdowns existing across the site. No existing posts referenced the old `python-dsa` tag at the time (checked `content/blog/` directly), so this was a clean rename, not a migration.
- **Known gotcha**: Decap CMS resolves `config.yml` as a relative URL. Visiting `/admin` without a trailing slash makes the browser resolve it against `/` instead of `/admin/`, 404ing regardless of browser — fixed via `<base href="/admin/">` in `admin/index.html`. Don't remove that tag.
- Netlify Identity + Git Gateway + the Google login provider are dashboard-only settings, not something committable — and Identity login only works on a real deployed domain, never on `localhost`.

## Progress tracker (`/gate-da-progress-tracker`, added 2026-07-21; slug renamed from `/progress` 2026-07-25 with no redirect from the old path)

A day-by-day study schedule tracker at `taai.live/gate-da-progress-tracker`, open to any student (no LMS/enrollment check — this is intentionally separate from `learn.taai.live`). First real backend/database this repo has ever had; everything else in this site is static.

- **Frontend**: `gate-da-progress-tracker.html` + `progress.js`. The nav is React/JSX ported verbatim from the other pages (added 2026-07-24, scoped light-theme CSS vars on `#nav-root` so it doesn't leak into this page's dark theme) — but the tracker itself (calendar, streak, pomodoro, etc.) is vanilla JS, no React/Babel. `progress.js` renders that part by building HTML strings and setting `innerHTML`, not a framework.
- **Backend**: Supabase (Postgres) accessed only through Netlify Functions in `netlify/functions/` — the frontend never talks to Supabase directly. `lib/supabase.js` and `lib/csv.js` hold shared helpers. Functions: `register`, `complete-task`, `streak`, `subject-progress`, `pomo-settings`, `pomodoro-complete`, `pomodoro-leaderboard`, `rename`, and `tracker-data` (a single consolidated endpoint for the page-load batch — see the gotcha below; it replaced 4 separate one-off functions that used to exist here: `schedule`, `progress`, `last-week-focus-leaders`, `pomo-sessions`).
- **Student identity**: cookie only (`taai_user`, base64-encoded JSON, 365-day expiry), no passwords/auth. `register.js` looks up-or-creates by email.
- **Schedule data flow — deliberately manual, no automatic external sync of any kind.** The user hands over each month's schedule directly (as a PDF or similar); convert it to `sheets/schedule.csv` (`Date | <Subject columns...>`, dates as `DD/MM/YYYY`, one cell = one task) and run `npm run load-schedule` (`scripts/load-schedule.mjs`) to load it into Supabase — validate through the real `parseCsv`/`toIsoDate` in `netlify/functions/lib/csv.js` first, don't hand-write SQL. There used to be a `sync-schedule.js` cron function pulling from a published Google Sheet; removed at the user's explicit request ("I will provide you the schedules, don't read from anywhere else") — don't reintroduce an automatic fetch from Sheets or any other external source without being asked.
- **Streak** (`streak.js`) and **subject-progress** (`subject-progress.js`) are both computed from the *entire* schedule history server-side, not from whatever month the client currently has loaded — a month-scoped version would make progress look like it resets every time the student navigates months, since e.g. a subject can span many months and a streak must span backward past the currently-viewed month.
- **"Progress by subject" always shows the full GATE DA syllabus**, not just subjects that happen to be scheduled yet — `CANONICAL_SUBJECTS` in `progress.js` is a hardcoded display-name list merged with whatever `subject-progress.js` actually returns; unscheduled ones show at 0%. Names are matched by exact string, so if a future month's sheet spells a subject differently than `CANONICAL_SUBJECTS` (or differently than an already-synced month did), it'll show up as an extra row instead of merging — keep this list's spelling in sync with whatever's actually typed into schedule PDFs/CSVs.
- **The "live now" pulsing dot exists on both leaderboards, not just the weekly top-20** (extended to the daily top-10 "Today" card 2026-09-04) — `fetchLiveStatusByEmail()` in `lib/supabase.js` is the one shared definition of "live" (running `pomo_active_session` row whose `phase_end_at` hasn't passed yet — see its own comment for why `running` alone isn't sufficient), used by both `pomodoro-leaderboard.js`'s weekly board and `fetchTodayLeaders()`'s daily leaders, so the two can't disagree on what counts as live. `progress.js`'s `liveDotHtml()` (previously only called from the weekly `renderLeaderboardRows`) is now also called from `renderTodayLeaderboardRows` and the daily viewer-rank row.
- **The Pomodoro settings gear scrolls its panel into view on open** (`pomo-settings-toggle` click handler, `progress.js`, fixed 2026-09-03) — the panel sits at the very bottom of `.pomodoro-card`, below the ring/dots/controls/notify-tip, so on a short viewport it could open entirely below the fold with nothing visibly changing on screen; a real report ("people who don't scroll are confused where did it come"). `panel.scrollIntoView({ behavior: 'smooth', block: 'nearest' })` fires only when the panel is being shown, not hidden.
- **Focus Mode has a Pomodoro timer** (circular depleting SVG ring, Start/Pause/Reset/Skip, session dots, a synthesized Web Audio chime on phase change). Durations + sessions-per-long-break are user-customizable via a settings panel, persisted in `localStorage` (`taai_pomo_settings`). Entering Focus Mode pushes a History API entry so the Back button exits it without leaving the page. A fresh navigation (typing the URL, clicking "Progress Tracker" in the nav, even to this exact page) always lands on the main checklist — the one exception is a genuine browser reload (F5/Cmd+R) while already in Focus Mode, which restores it, since a student mid-session refreshing isn't "starting fresh" the way a new visit is. Distinguishing "restore" from "land on checklist" needs *two* signals together, not just one: the Navigation Timing API's `entries[0].type === 'reload'` (specific to the actual reload action) decides *whether a reload should restore*, and a small `taai_focus_active` localStorage flag (set/cleared everywhere `state.focus` changes) decides *whether it currently should*. `history.state` alone can't do this — confirmed empirically, not assumed: Chromium can preserve/reuse the current session-history entry's pushState'd data across a fresh navigation to the exact same URL, not just an actual reload, so a stale `{focus:true}` can otherwise resurface later via the Back button from an already-exited session. For the same reason, the `popstate` handler in `progress.js` deliberately ignores `e.state` and just exits Focus Mode unconditionally whenever `state.focus` was true going in, rather than trusting whatever's attached to the entry being popped to.
- **Local dev needs `netlify dev`, not Docker** — the plain static server (`npx serve`) can't run `/api/*` Netlify Functions, so use `npx netlify-cli dev --port 8080` for anything touching `/gate-da-progress-tracker`. `netlify.toml` has a `[dev] publish = "."` block specifically so `netlify dev` serves source (live JSX transpile) like the plain server does, not `dist/`. **A local Docker Supabase stack (`supabase start`) used to be required for this — it isn't anymore.** `.env` points `SUPABASE_URL`/`SUPABASE_SERVICE_KEY` at the real cloud project (see below) for both local testing and production, so there's nothing to spin up locally at all. Only reach for `supabase start` again if there's a specific reason to test against a disposable/throwaway DB instead of the real one (it cost ~9GB of Docker images and needed manual teardown every session — avoid unless actually needed).
- **Production Supabase is set up** (as of 2026-07, project ref `ureoahmpgzmtqfnpirdi`) — `supabase/schema.sql` has been run against it, and it's the same project `.env` uses locally. Project-creation security settings: Data API **on** (required — that's what `supabase-js` actually talks to), "Automatically expose new tables" **off** (the frontend never talks to Supabase directly, only through `service_role`-authenticated functions, so there's no reason for the public `anon` role to see these tables at all), automatic RLS **on** (costs nothing since `service_role` bypasses RLS regardless — it's a default-deny backstop in case a table's public exposure ever changes by accident; this table holds student emails). Two gotchas from setting it up: (1) Supabase's newer UI defaults to `sb_publishable_...`/`sb_secret_...` format API keys, but `@supabase/supabase-js` v2.45 (what's pinned in `package.json`) was built/tested against the older JWT-format keys — grab the `service_role` key from the **"Legacy anon, service_role API keys"** tab, not the new default one. (2) The Project URL shown in the dashboard's "Data API" settings includes a trailing `/rest/v1/` — strip that before putting it in `SUPABASE_URL`, the client library appends that path itself. **Netlify's own dashboard env vars still need to be set separately** (same two values) for the *live* site to work — `.env` only affects local `netlify dev`, it has no bearing on the deployed site.

## Discord bot + /team console (added 2026-08-29 through 2026-09-02)

Posts to Discord automatically, reusing the progress tracker's existing leaderboard data. **Rearchitected 2026-09-02** from 3 hardcoded, fixed-cron functions into a general scheduler (`scheduled_posts` table + `discord-dispatch.js`), managed from a new authenticated page (`/team`) — driven by the ask to control "any post in any channel... text, tagging, date, time, frequency, repeatability," not just the original 3.

- **Why a dispatcher, not one cron per post**: Netlify Scheduled Functions run on a cron baked into `netlify.toml` at *deploy* time — a page can't change when a function fires, only what it does when it fires. So a user-editable schedule can't map to "one cron per post." Instead, `netlify/functions/discord-dispatch.js` runs on one fixed, frequent cron (`*/15 * * * *`, every 15 minutes — see `netlify.toml`) and queries `scheduled_posts` for anything due (`enabled AND next_fire_at <= now()`), firing each row independently (one row's failure doesn't block the others) and recomputing `next_fire_at` for recurring types via `computeNextFireAt()` in `lib/supabase.js` (`'once'` posts just get `enabled = false` instead).
- **`scheduled_posts`** (`supabase/schema.sql`): one row per post. `source` is either `'custom'` (literal `title`/`body` text) or one of 4 built-in dynamic sources — `'daily_leader'` (yesterday's single top student), `'daily_leaderboard'` (yesterday's top 3, added 2026-09-02 once a single winner wasn't enough), `'weekly_leaderboard'` (last week's top 5), `'monthly_consistency'` — which pull live data via the same `fetchTodayLeaders`/`fetchLastWeekLeaders`/`computeMonthlyConsistency` helpers the tracker page itself uses. `title`/`body` are always an optional override template (via `renderTemplate()`) that falls back to the original hardcoded wording when blank. Placeholders: the single-entity sources (`daily_leader`, `monthly_consistency`) get `{{name}}`/`{{hours}}` for the one student, and `body` there fully replaces the default sentence when set. The ranked-list sources (`daily_leaderboard`, `weekly_leaderboard`) get per-position placeholders instead — `{{name}}`/`{{hours}}` for 1st, `{{name2}}`/`{{hours2}}` for 2nd, up through `{{name5}}`/`{{hours5}}` for the weekly top 5 (see `rankedVars()` in `discord-dispatch.js`), an unmatched placeholder (e.g. `{{name4}}` on a top-3 post) just rendering blank rather than erroring — but there, `body` is only an **intro line shown above** the medal list, never a replacement for it (the list itself always renders, by request, matching how `monthly_consistency`'s intro + runner-up list already worked). Each row carries its **own** `webhook_url` — not the shared `DISCORD_WEBHOOK_URL` env var — so different posts can genuinely target different channels; the env var is only `postToDiscordWebhook()`'s fallback default for any caller that doesn't pass one explicitly.
- **Monthly "most consistent student"** (the `'monthly_consistency'` source, reports on the month that just closed — an Oct 1 firing reports September): ranks by **median** daily focus minutes, zero-filled across every calendar day of the month (every day counts as a real work day here, no rest-day concept exists in this schedule), not a raw average, so one huge binge day can't outrank someone who studied moderately but genuinely every day. Only students registered by the **7th** of that month are eligible. Ties broken by total minutes. **August 2026 was deliberately never computed** — `pomo_daily_sessions.total_minutes` only started actually populating on Aug 28 (see the known-gotcha below), so a full-August calculation would zero-fill 27 of 31 days for nearly every student regardless of real activity.
- Built-in sources link back to `https://taai.live/gate-da-progress-tracker` two ways: the embed title itself (Discord makes a titled embed's `url` clickable) and an explicit `[📊 View the progress tracker](...)` markdown link line in the body.
- **`/team`** (`team/index.html` + `team/team.js`) — the only place `scheduled_posts` rows are ever created/edited/deleted (`netlify/functions/team-posts.js`, a role-gated REST-style CRUD function: GET/POST/PUT/DELETE). Gated by **Netlify Identity**, the same login already powering the blog CMS at `/admin` — but requiring the **`admin` role specifically** (`requireAdmin()` in `lib/supabase.js`, checking `context.clientContext.user.app_metadata.roles`), not just "any logged-in Identity user", since a blog writer sharing that same login has no reason to reach student data or webhook controls. The `admin` role is assigned per-user in the Netlify Identity dashboard — a one-time manual step, not something committable (same category as Identity/git-gateway setup itself). Netlify Functions auto-populate `context.clientContext.user` from a valid Identity JWT in the request's `Authorization` header — no custom JWT verification code needed, same mechanism git-gateway already relies on.
- **Mentions**: `scheduled_posts.tag_everyone` (checkbox) and `.extra_mentions` (free text, added 2026-09-02 — `@here`, a role `<@&ROLE_ID>`, a specific person `<@USER_ID>`; there's no Discord API integration to look up names, so the exact raw mention syntax has to be typed/pasted in) combine into one `content` string via `buildMentionContent()` in `lib/supabase.js` (e.g. both set becomes `"@everyone <@&123>"`). `postToDiscordWebhook()` takes this as its `content` argument — Discord silently drops even literal mention text in a webhook's `content` unless the request also sets `allowed_mentions: { parse: [...] }` (a deliberate anti-spam safeguard), which the helper only adds when `content` is actually non-empty. `/team`'s Preview button shows this line too (`team-posts.js`'s `?preview=1` response includes `content` alongside `embed`).
- **A "? Syntax reference" toggle lives on `/team` itself** (`renderReference()` in `team.js`, added 2026-09-02) — sources, placeholders, mention syntax, all documented in the page for whoever's creating a post, not just in this file. Keep it in sync whenever a source/placeholder/field changes, same as this doc.
- **"Send Test" actually posts, "Preview" never does** — both resolve content identically (`resolveScheduledPostEmbed`/`buildMentionContent`), but Preview (`?preview=1`) only returns JSON for the page's own styled approximation, while Send Test (`?test=1`, added 2026-09-02) genuinely calls `postToDiscordWebhook()` — always against the form's separate, optional **`test_webhook_url`** field (persisted per-row purely as a UI convenience, never read by `discord-dispatch.js`), never the row's real `webhook_url`. This is how a wording/mention change gets verified against an actual Discord client's real rendering before it's trusted with the production channel — same discipline as every manual test this session, just built into the page instead of requiring `.env` swapping.
- **Custom posts get top billing over the recurring daily/weekly/monthly ones** (`renderPostList()` in `team.js`, added 2026-09-04) — the built-in leaderboard posts are edited rarely (set once, left alone), while custom posts (a weekly schedule, a one-off announcement) are what actually gets touched often; showing both with equal weight meant re-scanning the same untouched rows every visit. Custom posts (`source: 'custom'`) render first, always visible, under a "Custom announcements" heading; the built-in ones collapse behind a "Show recurring leaderboards (N)" toggle, closed by default (`state.showBuiltIn`) — same collapsed-by-default pattern as the syntax reference panel.
- **The page is organized around channels, not one flat list** (added 2026-09-03): the post list groups rows into a card per channel (`renderPostGroups()` in `team.js`) instead of one undifferentiated list — matters once there's more than one real channel in use, so it's obvious at a glance which Discord channel a given post goes to without reading each row's URL. Grouping key is `webhook_url`, not the `channel_name` text (changed 2026-09-04) — `channel_name` is only ever a display label, so two rows are "the same channel" only if they actually post to the same place; grouping by the label text instead would silently split one real channel into two groups if a row was ever left unlabeled or typo'd. The displayed heading is the first non-blank `channel_name` found in that group (`groupLabel()`), falling back to a shortened webhook tail if every row in the group is unlabeled. **A ✎ button on each heading renames the channel everywhere it's used** (added 2026-09-04, `state.renamingWebhook`/`renameStatus`) — since `channel_name` is duplicated per-row rather than being a single shared entity, renaming means finding every post whose `webhook_url` matches the group and `PUT`-ing each with its full existing payload, only `channel_name` changed (never a partial payload — team-posts.js's PUT handler expects the complete row shape, so reusing each post's own already-fetched object as the base and overriding just that one field is what avoids silently blanking out its webhook/schedule/etc.). The create/edit form is likewise split into 4 labeled sections (Destination / Content / Mentions / Schedule) rather than one long flat list of fields.
- **A 'custom' post can carry multiple subjects' schedules, merged into ONE date-ordered list inside a single embed, via `sections`** (`scheduled_posts.sections JSONB` — `[{title, rows: [{date, task, time}]}]`, added 2026-09-04, restructured same day) — built for the weekly-schedule-to-Discord use case. **Design history matters a lot here — three different layouts were tried and each explicitly rejected before landing on the current one**: subjects side-by-side in one embed's `fields` ("too congested"); each subject as its own separate stacked embed ("the subjects are divided into different cards" — everything needs to read as one card); each subject as its own bold-headed *text section* within the one embed, subject-first order ("the order of mention of everything should be date wise and also mention weekday"). What shipped: `resolveScheduledPostEmbed()`'s `'custom'` branch flattens every section's rows into one list, sorts by `date`, groups consecutive same-date rows, and renders one bold `"Weekday, Mon DD"` heading per calendar date with that date's tasks underneath (subject-prefixed, since one date can span several subjects) — see `formatDateHeading()` and the function itself for the exact algorithm. `date` is a real `<input type="date">` value on the `/team` form (not free text) specifically because reliable chronological sorting and weekday lookup aren't safely derivable from an arbitrary typed string like "15th June" — sorting works as plain string comparison since ISO `YYYY-MM-DD` values sort correctly that way. Every source's branch still returns `[{...}]` (an **array**, usually length 1) from `resolveScheduledPostEmbed()`, and `postToDiscordWebhook(embeds, content, webhookUrl)` still takes that array directly — this plumbing was built for genuine multi-embed support and is harmless to keep even though `'custom'` doesn't currently need more than one embed. `/team`'s create/edit form shows an "Extra sections (optional)" area — only for `source: 'custom'` — with a **Subject** dropdown (added 2026-09-04, was free text — `SUBJECT_OPTIONS` in `team.js`, built from the centralized subject list below, paired with a locally-owned emoji per subject purely for the Discord post's own styling; `subjectOptionsHtml()` always includes the field's current value as a selectable option even when it isn't one of the 10, e.g. free text saved before this became a dropdown, so opening an old post never silently swaps its subject on save — short by design, since it repeats on every one of that subject's lines in the final post now, not shown once as a heading, so module-name detail belongs in the main Title/Body instead) plus a repeatable Date/Topic/Duration table per section (`renderSectionsEditor()`/`readSectionsFromDom()` in `team.js`). No per-section color field — only one embed exists, so only the post's own top-level **Card color** field (added alongside Title/Body in the Content section) applies. Add/Remove reads existing rows back from the DOM first (not from `state.editing`, which is otherwise only synced on submit) so adding one more section doesn't wipe out ones already typed. `sections[].rows` (real date/task/time values) is the only thing persisted per section now — no derived markdown body is stored, so re-opening a saved post for editing just uses the saved rows directly, nothing to parse back out of generated text.
  - **Multi-batch schedules stay outside this system, by design** — there's no "batch" concept anywhere in `schedule_tasks`/`students` (confirmed by checking, not assumed), so a per-batch weekly schedule (e.g. "Batch A" vs "Batch B", each with its own subjects/channel) can't be pulled automatically. The `sections` feature only makes hand-typing that weekly post through `/team` *possible*, not automatic — someone still manually types each week's schedule into the form. Two separate `scheduled_posts` rows (one per batch, each with its own `webhook_url`) is the right setup once real batches exist — same pattern as any other per-channel post, and each is its own single-embed post (see above), never combined into one multi-batch message.
  - **Within a date's task line, duration is an inline-code chip** (`` `1h25m` ``) straight after the task — arrived at through extensive live testing against a real test webhook (not just visual guessing), same discipline as the date-ordering change above. Rejected along the way: inline-parenthesized duration (felt "too intertwined with the text"), a separate line with manual space-character indentation (confirmed unreliable — Discord doesn't render extra space/ideographic-space characters as real indentation), and a monospace code-block table (tried twice, both wrapped badly on real devices — "captured only one subject", "spread out"). No blank line between entries (tried — "not compact"). Two different batches must be **two separate messages**, never combined into one multi-batch post even with a divider between them (tried — combining always read as "too much content," regardless of how the boundary was marked).
- **A "Load a saved channel" dropdown** (`renderChannelSelect()`/`getKnownChannels()` in `team.js`, added 2026-09-03) sits above the Webhook URL field on the create/edit form — options are the distinct `webhook_url`s already used by existing rows (deduped, labeled by `channel_name`, or a shortened URL tail if never named), so a new post to an already-known channel doesn't need the webhook pasted in again. Picking one directly patches the Webhook URL/Channel name `<input>`s via the DOM (not `state.editing` + a full `render()`) specifically so it doesn't blow away anything already typed into Title/Body — those only sync into `state.editing` on submit, so a full re-render at that point would rebuild the form from stale state and silently drop them. Still just a starting point, not a lock — both fields stay freely editable afterward, same as if typed by hand.
- **The Body box pre-fills with the current default wording** for `daily_leader`/`monthly_consistency` (`DEFAULT_BODY_BY_SOURCE` in `team.js`, added 2026-09-02) whenever there's no real custom body saved yet — so editing starts from the actual current sentence instead of an empty box someone has to reverse-engineer. Kept as a duplicated literal (not fetched from the server) since it's just two short strings; **must be updated by hand alongside `resolveScheduledPostEmbed`'s own defaults in `lib/supabase.js`** if that wording ever changes, or the two will silently drift. Ranked-list sources (`daily_leaderboard`, `weekly_leaderboard`) have no equivalent — blank there is itself a valid, common choice ("no intro line"), not something needing a default filled in.
- **Migrating off the 3 old standalone functions** (`discord-daily-leader.js` etc., removed 2026-09-02): `scripts/seed-scheduled-posts.mjs` inserted 3 rows reproducing their exact prior behavior (same webhook, same default wording, same timing) before the old files and their `netlify.toml` cron entries were deleted — verified locally (dispatcher fires all 3 built-in sources correctly, plus `'custom'`/`'once'`/`tag_everyone` paths) against a **test-channel webhook**, never production, before cutting over.
- **Testing `discord-dispatch.js` directly**: `netlify dev` allows invoking a scheduled function via a plain `GET`/`curl` regardless of its cron schedule (e.g. `curl localhost:8080/.netlify/functions/discord-dispatch`) — it'll print a warning about being "a scheduled function... invoked via HTTP," which is expected and harmless. To force a specific row to fire for testing, backdate its `next_fire_at` in Supabase rather than waiting for the real time.
- **`/team`'s real login flow can only be verified on the deployed site** — Identity login never works on `localhost` (same limitation as `/admin`'s Decap CMS). Locally, `team-posts.js`'s logic is instead verified by invoking its `handler()` directly in a Node script with a hand-built `context.clientContext.user` (bypassing real HTTP/JWT), which still catches real bugs (auth gating, validation, `next_fire_at` computation) without needing a real domain.
- **Content resolution lives in `lib/supabase.js`, not `discord-dispatch.js`** (`resolveScheduledPostEmbed()`, moved there 2026-09-02): both the real dispatcher and `/team`'s **Preview** button (`team-posts.js`'s `POST ?preview=1`) call this exact same function — a preview built from separate, similar-but-not-identical logic could quietly drift from what actually posts, so there's deliberately only one code path for "what does this row's content look like." Preview passes an in-memory object built from the form's *current, possibly-unsaved* values (never a real row, never persisted, never actually posted to Discord) — safe to click regardless of which webhook `.env` happens to have loaded locally.
- **`/team` is two mutually-exclusive tabs, not stacked panels** (`state.tab` in `team.js`, restructured 2026-09-03) — Announcements (the Discord `scheduled_posts` list/form/reference panel) and Students are never rendered together; switching tabs replaces the page body rather than appending a panel above the other one. This replaced an earlier version where the Students table was just a toggle that appended above the still-visible post list — a real complaint ("the discord messages and other announcement stuff should be located differently from this academic stuff"), since a student-performance table and a Discord-post CRUD list are unrelated concerns that shouldn't share screen space. Each student's email is a real `mailto:` link directly under their name, always visible (no extra click to reveal it) — a one-click way to email them, not just plain text.
- **A "Students" view on `/team`** (`netlify/functions/team-students.js` + `renderStudents()`/`loadStudents()` in `team.js`, added 2026-09-03) — for spotting high performers (and students who've gone quiet), separate from `scheduled_posts` entirely. `GET /api/team-students` batches one query per table (students, `schedule_tasks`, `task_progress`, `pomo_daily_sessions`, this week's `pomodoro_stats`) rather than looping a per-student query like `streak.js` does for one student — same batching principle `pomodoro-leaderboard.js` already uses, just extended to every student instead of one board's worth of rows. Returns each student's all-time focus hours, this week's hours, a **Consistency** figure, **Course progress** percentage, streak (via the same `computeStreak()` `streak.js` uses), completed-task count, last-active date, and a free-text `notes` field — sorted by all-time hours descending by default (so high performers float to the top on load), with clickable column headers to re-sort client-side (e.g. by Consistency for steady-but-not-flashy students, or Last active to see who's dropped off). Consistency is median daily focus minutes, zero-filled per quiet day — the same measure `computeMonthlyConsistency()` uses for the Discord monthly post — but deliberately **not** the same lookback: that function reports on a month that's already fully closed, while this is a live, in-progress reading zero-filled only across days that have actually happened *so far* this month (filling in not-yet-arrived future days as zeros would artificially crater everyone's median early in the month). Reporting on last month instead would inherit the same degenerate-data problem the monthly Discord post itself hit for August (`pomo_daily_sessions.total_minutes` only started populating Aug 28, so a full month would zero-fill ~27 of 31 days for almost everyone) — a live current-month reading sidesteps that and stays meaningful for an ongoing admin view even though it means small sample sizes early in a month. Course progress is `student's completed tasks ÷ every task in schedule_tasks` (the same whole-schedule denominator `subject-progress.js` uses per-subject, here rolled into one overall percentage instead of a per-subject breakdown, which wouldn't fit a 300-row table) — since `schedule_tasks` only ever holds months already loaded (see "Schedule data flow" above), this is naturally "of what's been assigned so far," not some far-future total. `notes` (`students.notes`, added 2026-09-03) is purely for the team's own reference — no effect on tracker behavior — edited inline per row and saved via `PATCH /api/team-students`.
- **`scheduled_posts.channel_name`** (added 2026-09-02) — a free-text label purely for `/team`'s own display (e.g. "#announcements"), no functional effect on where a post actually goes (that's still `webhook_url`). Without it, telling rows apart in the list means decoding opaque webhook URLs by eye; `/team`'s post list falls back to a shortened webhook URL only when this is blank.

## Git remotes

Push reaches **both** `github.com/taai2025/TAAI` (primary) and `github.com/diptadee2/TAAI` (the user's personal mirror) via origin's dual-pushurl config. Plain `git push` is sufficient — don't add `--force` or push to only one remote unless asked.

## Known gotchas worth not re-discovering

- **A blog post's Markdown body can embed raw HTML (`marked` passes it through), but every line must start at or near column 0** — CommonMark treats a line indented 4+ spaces, once it starts a new block (e.g. right after a blank line), as an *indented code block*, not raw HTML, even mid-way through an otherwise-fine HTML section. Hit this directly writing a heavily-nested custom-design post (`content/blog/gate-da-syllabus-2027.md`): several `<div>` blocks silently turned into escaped `<pre><code>` text instead of rendering, purely because they carried the source article's original 4-8 space indentation. Fix: strip all leading whitespace from HTML content going into a post's Markdown body — indentation is a purely cosmetic authoring habit here, not something the renderer tolerates the way a browser parsing plain HTML would.
- **A post can carry its own bespoke design (fonts, colors, custom `<style>`) safely by scoping every custom property and selector to a wrapper class** (e.g. `.gda-article`) **instead of `:root`/bare `body`** — blog.css already defines `--ink`/`--line`/etc. globally for the shared nav/footer chrome; a post's own `:root{--ink:...}` would silently override those site-wide, breaking the nav/footer's colors, not just the post's own content. Verified this doesn't leak by checking the real computed color of a nav element after loading such a post.
- **Chromium DOM-node leak**: animating `transform` or `box-shadow` directly on an element that *also* has both `box-shadow` and `border-radius` causes an unbounded detached-node leak (confirmed via CDP `Performance.getMetrics`). Animate a wrapper or pseudo-element instead, leave the shadow+radius element itself unanimated.
- **WebGL/Canvas effects are expensive per-tab** (measured via renderer+GPU process RSS, not JS heap — heap snapshots show nothing here): a `gsap`-driven Canvas2D effect cost ~150-200MB/tab from its continuous ticker; an `ogl`-based WebGL shader background cost ~300MB from context creation itself, independent of resolution. A zero-dependency Canvas2D effect with no continuous external library ticker (`DotField` in `courses.html`) showed no measurable cost. Prefer that pattern if a future visual effect request comes in.
- **Dev-server-only memory growth** from repeated live Babel recompilation during active navigation testing is expected and not a leak (confirmed via heap-snapshot diffing) — it does not affect production, since Netlify serves precompiled `dist/`.
- **Favicon**: the 16×16 frame inside any `.ico` built via ImageMagick gets forced to 1-bit alpha regardless of source quality — that's why standalone `favicon-16.png`/`favicon-32.png` exist as preferred `<link rel="icon" type="image/png">` tags ahead of the `.ico` fallback.
- **Server-side "today" must be computed in IST, never naive `new Date()`**: Netlify Functions run on infrastructure with no guaranteed local timezone (effectively UTC). For roughly the first 5.5 hours of every IST calendar day, a naive `new Date().toISOString().slice(0,10)` silently returns *yesterday's* date by IST reckoning — bit us exactly this way in `streak.js` (a same-day tick wasn't counted). Use `todayIST()` in `netlify/functions/lib/supabase.js` (`Intl.DateTimeFormat` pinned to `Asia/Kolkata`) for any server-side calendar-date logic.
- **`@supabase/supabase-js` needs an explicit WebSocket transport**: `createClient()` eagerly constructs a Realtime client requiring a `WebSocket` constructor that isn't guaranteed across every Node/Lambda runtime a function might execute on — without it, every single request crashes. `lib/supabase.js` passes `realtime: { transport: ws }` (the `ws` npm package) to work around this; don't remove it even though nothing here actually uses realtime subscriptions.
- **`tracker-data.js` is deliberately one large function instead of several small ones** — it used to be 7 separate Netlify Functions (`schedule`, `last-week-focus-leaders`, `progress`, `streak`, `subject-progress`, `pomo-settings` GET, `pomo-sessions`), all only ever called together as one batch from `loadMonth()`. Each Netlify Function is an independent Lambda with its own cold-start lifecycle, so a page load after any idle gap paid up to 7 separate container-boot + Supabase-client-construction costs in parallel — confirmed via the Netlify Functions dashboard as the cause of a uniform 1.2-1.8s p50 latency on otherwise-simple single-table queries, plus inflated Web-requests credit usage. Don't re-split this back into one-function-per-query without re-checking whether that dashboard number regresses — `streak.js`, `subject-progress.js`, and `pomo-settings.js` are correctly still separate, since those are also called independently outside the page-load batch (after a task toggle, or a settings save).
- **Local Supabase (`supabase start`) doesn't auto-grant table privileges** the way a hosted project does — a table created via migration has no `service_role` GRANTs by default on the local CLI's Postgres image, so every query fails with "permission denied" even with correct credentials. `supabase/schema.sql` ends with explicit `GRANT SELECT, INSERT, UPDATE, DELETE ... TO service_role` — required for local dev to work at all, keep it even though hosted Supabase might not strictly need it.
- **Any script run with `.env` loaded hits the real production Supabase project, not a sandbox** — there's no separate local/staging database (see "Local dev needs `netlify dev`, not Docker" above). Seeding synthetic test rows directly via `getSupabase()` (rather than through `netlify dev`'s served app) is easy to reach for when testing backend logic in isolation, but it's real, live data the instant it's written — confirmed the hard way: seeding 20 fake high-minute `pomodoro_stats` rows to test the leaderboard's below-top-20 behavior briefly *displaced actual students* from the real top-20 leaderboard until cleaned up. Prefer mocking the HTTP response (e.g. Playwright route interception) over seeding real rows whenever the goal is testing frontend rendering; if a backend query genuinely needs live-data verification, clean up every row written immediately after and verify the real leaderboard/data is back to its prior state, not just that the delete call returned success.
- **`.fade-in` elements + a `fullPage` Playwright screenshot taken without scrolling can look like missing content** when they're actually present and correct — the IntersectionObserver-driven reveal hasn't fired yet for anything below the fold at capture time. Before treating a screenshot gap as a real bug, either scroll through first or run `document.querySelectorAll('.fade-in').forEach(el => el.classList.add('visible'))` to force-reveal everything, then re-screenshot.
- **Regenerating a `.fade-in` element's `innerHTML` replays its entrance animation from scratch**, even if the only actual change was a number. Hit this repeatedly in `progress.js` (streak card, subject-breakdown, heatmap all did this on every task toggle). Fix pattern used throughout: patch the specific value in place (`el.textContent = ...`, `el.style.width = ...`, `el.setAttribute('data-level', ...)`) instead of regenerating and reassigning a `.fade-in` ancestor's `innerHTML`.
- **Don't try to recolor native `<input type="number">` spin buttons for a dark theme** — tried `color-scheme: dark`, then an explicit `::-webkit-inner-spin-button { filter: invert(1) }`, and the arrows were still low-contrast/black in the user's actual browser both times (couldn't even verify visually in headless Chromium, which renders/suppresses them differently than a real browser). WebKit/Firefox/Safari each handle these hooks inconsistently. Just remove them (`-webkit-appearance: none` on the spin-button pseudo-elements, `appearance`/`-moz-appearance: textfield` on the input) — typing a number directly or the keyboard up/down arrow keys still work with the visual spinner hidden.
- **`CLIENT_VERSION` (the matching constant in `progress.js` and `netlify/functions/lib/supabase.js`) needs bumping on every real client-behavior change to `progress.js`, not only when a request/response payload shape changes.** It drives `checkClientVersion()` in `progress.js`, which polls `/api/version` every 2 minutes and force-`location.reload()`s a tab on a mismatch — the whole point being that an already-open tab picks up a fix automatically instead of running stale JS indefinitely. It went unbumped for 33 days across several real behavior-changing commits (including a genuine race-condition fix to the Pomodoro timer), which silently disabled that safety net for the entire window: `/api/version` kept returning the same string, so the check never tripped, even though the code underneath had materially changed. Any tab left open during that gap never got reloaded onto the fixes. Bump both copies together whenever `progress.js`'s runtime logic changes in any way a student could notice, not just on contract changes.
- **No `[[headers]]` block existed in `netlify.toml` until 2026-08**, so every static asset (images, favicons, the vendor React bundle) inherited Netlify's default `Cache-Control: public, max-age=0, must-revalidate` — the same "always revalidate, never cache" policy meant for HTML — forcing every repeat visit to re-download them in full. This was the single largest driver of Web bandwidth credits (checked via the account's Usage panel, not a guess). Fixed with a 7-day cache for `*.webp`/`*.png`/`favicon.ico`/`vendor/*` only — deliberately excludes HTML and actively-edited JS/CSS (`progress.js`, `blogs/blog.css`/`blog.js`) so shipped fixes keep showing up immediately instead of being stuck behind a stale cache. **`netlify dev`'s local "simple static server" fallback doesn't apply custom `[[headers]]`** even after a restart (confirmed: `curl -I` against localhost:8080 kept showing `max-age=0` post-restart) — this isn't a sign the config is broken, it's a known local-dev-only limitation; the production CDN does honor it. Don't waste time trying to verify cache headers via localhost.
